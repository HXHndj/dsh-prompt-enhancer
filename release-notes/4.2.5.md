# v4.2.5 — DSH 0.2.0-rc.1 兼容性适配（清单声明层）

> 升级到 DSH 0.2.0-rc.1 后插件被列表标为「**异常**」并**拒绝加载**（✨ 按钮与设置页入口都不出现）——原因不是插件代码坏了，而是 `package.json` 里两条 `peerDependencies` 的**版本范围**越过了新宿主的启动门禁。本版只改**清单声明**（外加一条新契约测试与三处文档同步）：`src/**`、`lib/client.cjs`、槽位名、RPC 面、全部客户端组件**零改动**。

## 🎯 根因（一句话）

DSH 0.2.0-rc.1 的 profile 启动门禁（`@deepseek-ai/dsh-app-boot` 的 `evaluatePluginCompatibility`）**只读** `peerDependencies`，把每一条 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的范围与**运行时版本**比对：

```js
semver.satisfies(runtimeVersion, range, { includePrerelease: true })   // runtimeVersion = 0.2.0-rc.1
```

**任一条不满足 ⇒ 整个插件被判不兼容并拒绝加载**（CLI 原文 `profile startup denies it`）。而 `^0.1.0-rc.6` 在 0.x 上等价 `>=0.1.0-rc.6 <0.2.0` —— 宿主一升到 `0.2.0-rc.1` 就被判死。旧版 0.1.7-rc.2 能用，只是因为它在那个区间的上界之内（同一份声明，纯版本驱动）。

## 🔧 修复内容

- **两条 dsh 系 peer 改双侧窗口 `>=0.1.5-rc.1 <0.3.0-0`**：`0.1.7-rc.2`（旧桌面线）与 `0.2.0-rc.1`（当前）都满足；上限用 `-0` 而非 `<0.3.0`，因为 DSH 主要走 `-rc` 发布 —— 裸 `<0.3.0` 会让未来的 `0.3.0-rc.1` **静默放行**，与「跨 minor 必须显式复核」的初衷相悖。
- **`dsh.client.inject` 去掉已淘汰的 `@deepseek-ai/dsh-client-runtime`**（npm 止于 `0.1.1-rc.2`，0.2.0-rc.1 的客户端启动图与 `app.asar` 内均无此包），换成 0.2 线真正提供 `ctx.slots` 的 `@deepseek-ai/dsh-client-ui-renderer`。注意 `dsh.client.inject` **没有任何阻断能力**（名字不在启动图里会被静默跳过），真正会拦插件的是 `peerDependencies`。
- **新增 `test/manifest-compat.test.cjs`（6 条零依赖契约）**：禁 `^`/`~`（0.x 上会隐式排除下一个 minor —— 正是本次根因）、必须双侧窗口、淘汰包名双向禁入、inject 形制与 slots 提供者在位、`engines.dsh` 与 peer 同源、版本/声明单一事实源。
- **文档更正**：`docs/compatibility-matrix.md` §4.1 原写「`dsh.client.inject` 不满足 ⇒ client 半部不注入」，与 0.2.0-rc.1 源码相反，已连同门禁口径一并更正；README（中/英）补「宿主版本边界」小节。
- **可选 `engines.dsh`**：与 peer 同窗口，纯作者声明（官方明示安装器/加载器**不强制**该字段，不要当门禁用）。

## ✅ 本次实测

- **真门禁函数复算**（0.2.0-rc.1 内 `evaluatePluginCompatibility` 的**逐字切片**，运行时版本由该包 `package.json` 提供，切片 sha256 `49e37cf0…`）：
  - 改前 `4.2.4` 声明 ⇒ `INCOMPATIBLE`，失败 peers 与报错文案与线上日志**逐字一致**（复现用户截图）；
  - 改后 `4.2.5` 声明 ⇒ `COMPATIBLE (undefined)`；
  - 强制 `0.1.7-rc.2` / `0.1.5-rc.1` / `0.2.1-rc.1` ⇒ COMPATIBLE；强制 `0.3.0-rc.1` / `0.3.0` ⇒ INCOMPATIBLE。**9 条断言全通过**。
- **npm 解析可行性**（CI 与用户侧安装的前置）：新范围在**严格 semver** 下由已发布版本满足，lock 实际解析到 `dsh-client-locale@0.1.5-rc.3` / `dsh-client-ui-renderer@0.1.5-rc.3`；对照组 `>=9.0.0` 按预期 `ETARGET` 失败（证明该检查有效）。
- **`npm test` 302 / 302 / 0 fail**；**`npm run gate` 通过 30 · 冲突 0**；`build-host --check` / `build-client --check` 双 OK（版本注入 4.2.5）。
- **DSH Desktop 0.2.0-rc.1 实机（用户执行安装并确认）**：装上本版改动后插件恢复可用——插件列表不再显示「异常」，用户回报「已完全适配 0.2.0-rc1」。口径说明：用户实装的那份 tgz 版本标签为 `4.3.0`（发布前按用户拍板改号），发布版 `4.2.5` 与之**内容相同、仅版本号不同**（门禁实际读取的 peer 范围 / `dsh.client.inject` / `engines.dsh` 逐字未变）。
