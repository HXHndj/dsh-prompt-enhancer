# v4.3.0 — 运行参数严格照办 + 超时逻辑重构

> **你设 30s，它就按 30s 执行。** 本版修掉一条长期潜伏的宿主行为：当模型链上任一条开启了「思考等级」（`reasoningEffort`）时，宿主会把用户设置的**超时静默放宽为 ≥120s**、**输出 Token 放宽为 ≥8000**，设置页与日志却仍显示用户值——用户设 30s/2000，实际按 120s/8000 跑，全程无告知。同时重构超时链路：原实现只靠 `iterator.return()` 取消，流阻塞在 `await next()` 时会排队失效，超时形同虚设。

## 🎯 根因（两处，均已实测复现）

1. **宿主静默放宽用户设置**：`state.timeoutMs = cfg.timeoutMs > 0 ? (链含 reasoningEffort ? Math.max(cfg.timeoutMs, 120000) : cfg.timeoutMs) : 0`，以及请求体的 `...(entry.reasoningEffort ? { maxTokens: Math.max(maxTokens, 8000) } : ...)`。两处都只改运行时值，任何用户可见处都不体现。
2. **超时中断是「协作式」的**：超时只置标记 + 调 `iterator.return()`；当流正阻塞在 `await iterator.next()`（首字迟迟不来/连接半死）时，`return()` 必须等当前 `next()` 结算才生效 ⇒ 计时器「响过」但请求迟迟不返回。

## 🔧 修复内容

- **严格照办（BREAKING）**：删除两处放宽，**设置值 = 实际下发值**。`0` = 无限制语义原样保留（不挂超时表 / 不下发 `maxTokens` 字段）。响应新增 `applied`（实际生效的三项参数），供「设置值 === 运行值」回归断言。
- **超时 = 从收到请求起的总墙钟预算**：覆盖 prepare/assemble、链上每一跳、首响应看门狗（15s）、连通性探测（12s/条）与两轮 pass；**不再逐段顺延**。
- **AbortSignal 真取消**：`AbortController.signal` 透传 `llm.stream({ signal })`（DSH 契约原生支持，适配器侧 `AbortSignal.any([consumer, signal])`），真正掐断在途 HTTP 请求。
- **到期硬返回**：超时与用户取消共用「中止即结算」通道，`Promise.race` 保证 RPC 在预算内返回 `TIMEOUT` / `ABORTED`——即便第三方 provider 不认 signal，界面也不会永远停在「正在优化」。
- **探测/看门狗有界**：二者窗口取 `min(原值, 剩余预算)`，预算耗尽即不再发起新动作。
- **日志说真话**：`[enhance] try … maxTokens=… timeout=…` 打印**实际下发值**（旧实现打印用户配置值，曾出现「日志说 2000、请求实际 8000」的误导）。
- **客户端可见抬高（替代运行时改写）**：思考等级「关→开」那一刻，把低于建议下限、且不为 0 的项**可见地写进配置**（超时 120s / Token 8000）+ 一次性通知行；设置页常驻建议行 + 「应用建议值」按钮。用户手动改回 30s 后**不会再被抬**。
- **删除误导提示行**：设置页原「当前模式默认：超时 30s · Token 2000 · 输出上限 8000」只描述档位默认、与生效值无关，整块删除（含 i18n 两键与死 CSS）。
- **超时提示带实际预算与去处**：「请求超时（30s 内未完成），已恢复原文；可在 设置 → 提示词增强 → 运行参数 中调高超时时间」。
- **配置一致性**：客户端 `sanitize` 接受 `0`=无限制（此前刷新即被丢弃，「无限制」存不住）；「✓ 已保存」纳入宿主 `config/set` 回执（不再谎报成功）；启动期不再被磁盘旧配置整体覆盖（仅 localStorage 为空时才采纳，未来格式 `version>2` 不回推）。

## ⚠️ 升级注意

- **推理链下的参数差异不再由宿主兜底**：开启思考等级且 Token/超时偏低时，可能出现空响应或超时——这是「严格照办」的预期结果，设置页会给出建议值与一键应用。
- **必须完整重启 DSH**（不是刷新页面）：插件**宿主半部** `plugin-host.js` 在进程启动时一次性加载，**客户端半部** `lib/client.cjs` 随页面刷新重取。只更新文件不重启会出现「新 UI + 旧宿主」的假阴性（新设置页已显示建议行，超时仍按旧逻辑 120s 执行）。
  判定运行中的是哪个半部：设置 → 提示词增强 → **诊断日志**里看 `[enhance] cfg … timeout=`（旧宿主 120000 / 新宿主按你的设置），超时触发时会多一行 `[enhance] abort hard-return … budget=`。

## ✅ 本次实测

- **产物级计时**：设置 **1000ms 预算 + 5000ms 挂起流 ⇒ 1009ms 硬返回 `TIMEOUT`**（旧实现要等满 5000ms 的流）；`cancel` 154ms 返回 `ABORTED`；`llm.stream` 实收 `AbortSignal` 且到期 `aborted === true`。
- **严格照办**：真实配置（`reasoning.effort=max` + `timeoutMs=60000`）驱动产物 ⇒ 日志 `timeout=60000`（旧 120000）、请求实收 `maxTokens` = 用户值（旧被抬到 8000）、`applied` 与配置逐字段相等。
- **测试与门禁**：`npm test` **321/321 通过**（基线 302，新增 19 条）；`npm run gate` **30 通过 / 0 冲突**；`build-host|build-client --check` 双 OK。
- **用户实机验证**：产物部署后经真实会话确认修复生效（设置 60s 不再被静默抬成 120s、到点返回）。
